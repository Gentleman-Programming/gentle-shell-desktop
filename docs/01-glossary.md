## Workflow

| Term | Definition | Where it lives | In the desktop |
|---|---|---|---|
| **feature document** | `odd/tasks/<feature-name>.md` plus its Engram mirror `odd/<feature-name>/tasks`. The model creates it before the first write of substantial work. No gentle-shell code reads or writes it, and its format is not specified ([05 O3](05-capability-inventory.md#odd-workflow-and-task-tracking)). | `GS:extensions/gentle-ai.ts:1254` | Not displayed (search Q32); gap [G2](04-rpc-contract.md#gaps-the-desktop-needs). The desktop repository keeps its own feature documents for M1 and M2 (`gentle-shell-desktop@5ab4a00:README.md:68-73`). |
| **ODD** (Organic Driven Development) | The predefined workflow of the gentle-shell harness, run on every request in seven steps: authorize, explore, resolve uncertainty, classify, track before the first write, implement task by task, close. gentle-ai's README presents it too. | `GS:extensions/gentle-ai.ts:1248-1256`; `GA:README.md:110` | No ODD panel yet: M3 (`gentle-shell-desktop@5ab4a00:README.md:63`). The mockup's ODD panel is intent, not spec ([05 O1–O4](05-capability-inventory.md#odd-workflow-and-task-tracking)). |
| **ODD phase** | The current ODD step, reported by the model through the `gentle_odd_phase` tool (`authorizing`, `exploring`, `researching`, `deciding`, `planning`, `implementing`, `checking`, `closing`, or `clear`) and otherwise inferred from tool activity. | `GS:lib/odd-phase.ts:16-25` (the eight phases); `clear` and the tool in [05 O2](05-capability-inventory.md#odd-workflow-and-task-tracking); `GS:extensions/gentle-ai.ts:1257` | Not surfaced. Inferred phases never leave the TUI editor ([05 O2](05-capability-inventory.md#odd-workflow-and-task-tracking); [04 §TUI-only surfaces](04-rpc-contract.md#gentle-shell-surfaces-that-do-not-reach-an-rpc-host)). |
| **RDD** (Receipt-Driven Development) | gentle-ai's native review of a finished candidate. It "reviews a finished candidate without taking ownership of delivery". It is a user-owned switch, `gentle-ai review mode enable\|disable\|status`, on by default and opt-out at v3.7.0: an unset mode resolves to on. Note: gentle-shell contradicts this in its README, "RDD is opt-in" (`GS:README.md:290`), and in its code, "RDD is off by default until explicitly enabled" (`GS:extensions/gentle-ai.ts:5205`). | `GA:docs/architecture/organic-rdd.md:5`, `:17-19`; `GA:README.md:134`; `GA:internal/cli/review_mode.go:48-49`; `GA:internal/reviewtransaction/rdd_mode.go:698-701`; gentle-shell command `/gentle:review-mode` (`GS:docs/readme-reference.md:395`) | Not surfaced (search Q29). The mockup status bar shows `ODD · RDD on` ([05 R1](05-capability-inventory.md#review-and-rdd); gap [G7](04-rpc-contract.md#gaps-the-desktop-needs)). |
| **receipt** | The word in RDD's name (Receipt-Driven Development). At v3.7.0 the docs say that after a successful acknowledgement ("burn"), "no terminal receipt, tombstone, witness, mirror, or delivery authority survives", and that gentle-pi has "no durable receipt". `UNVERIFIED:` no current definition of a receipt as a stored artifact was found in gentle-ai v3.7.0's README or `docs/review-integration.md`. | `GA:docs/review-integration.md:81`; `GA:docs/architecture/organic-rdd.md:50`; `GS:docs/review-integration.md:15` | Nothing to surface. |
| **review** (native review) | The RDD lifecycle owned by gentle-ai. It freezes the candidate, assesses risk, and picks the depth: passive gets a structural readback with zero reviewer lenses, medium one lens, high the four lenses Risk, Resilience, Readability and Reliability. It allows at most one bounded correction and closes with one acknowledgement. Delivery stays with the human. | `GA:README.md:132-134`; gentle-shell tools `gentle_review*` ([05 R5](05-capability-inventory.md#review-and-rdd)) | `confirm` dialogs render as cards; tool cards and the `gentle-pi.review-preflight` custom message are dropped ([05 R2–R5](05-capability-inventory.md#review-and-rdd); [audit A6](03-architecture/audit.md#a6-reducer-drops-non-assistant-messages-from-the-live-view)). |
| **todo list** | gentle-shell's `todo` model tool and its card widget `gentle-todo`. Open tasks are injected each turn. Its full state rides in each `todo` tool result as `details.gentleTodo`. | [05 O4](05-capability-inventory.md#odd-workflow-and-task-tracking) (`GS:extensions/gentle-todo.ts:200`) | Not surfaced (search Q30). The card widget is TUI-only. |
| **YOLO** | A session-only permission: the agent may implement, commit, push and open PRs within the already authorized task without asking each time. Destructive operations still ask. Default off. Activation needs the interactive primary TUI. | `GS:docs/yolo-mode.md:3-5`; `GS:lib/yolo-session-policy.ts:5-6` | Cannot be enabled from the desktop; the `gentle:yolo` indicator is ignored ([05 Y4](05-capability-inventory.md#safety-and-permissions); [04 §gentle-shell additions](04-rpc-contract.md#gentle-shell-additions-over-rpc)). |

## Protocol

| Term | Definition | Where it lives | In the desktop |
|---|---|---|---|
| **`extension_ui_request`** | pi's RPC record for an extension's UI call. Dialog methods (`select`, `confirm`, `input`, `editor`) block until the client answers with an `extension_ui_response` carrying the same `id`. Fire-and-forget methods (`notify`, `setStatus`, `setWidget`, `setTitle`, `set_editor_text`) expect no answer. | `PIDOC:rpc-extension-ui.md:7-8` | All four dialog kinds render as cards. Of the fire-and-forget methods, only `setWidget` with key `gentle-agents` is parsed ([04 §Extension UI requests](04-rpc-contract.md#extension-ui-requests)). |
| **`gentle-agents.activity/v1`** | The schema of the live helper state gentle-shell pushes to an interactive host: one bounded JSON document per coalescing window, sent through `setWidget` with key `gentle-agents`. | `GS:docs/gentle-agents-activity.md:1-13` | Parsed by `D:main/domain/rpc/helpersActivity.ts`; a frame with any other `schema` value is rejected (constant at `:19`, check at `:48`). Status and tool-item mismatches: [audit A5](03-architecture/audit.md#a5-helper-status-set-and-tool-items-do-not-match-gentle-shell). |
| **interactive host** | An RPC client that runs `pi --mode rpc` itself, "such as the Gentle Shell desktop app". It is enabled only by `GENTLE_SHELL_INTERACTIVE_HOST=1` (exact value). It turns on `ask_user_question` / `ask_user_choice` dialogs and the helper activity push. Subagent children never inherit it. | `GS:docs/gentle-agents-activity.md:3`; `GS:lib/rpc-host.ts:8`, `:15-17`; `GS:docs/readme-reference.md:374` | Set on every spawn (`D:main/domain/session/PiSession.ts:67`, `:134`); [ADR 0012](03-architecture/adr/0012-interactive-host-env-flag.md). |
| **`notify`** | A fire-and-forget extension UI message with an optional `info`, `warning` or `error` type. Most `/gentle:*` commands answer only with `notify`. | [04 §Extension UI requests](04-rpc-contract.md#extension-ui-requests); [05 V18](05-capability-inventory.md#shell-experience) | Ignored (`D:main/domain/rpc/chatReducer.ts:182-184`), so most `/gentle:*` output is invisible ([05 C20](05-capability-inventory.md#conversation-and-input)). |
| **RPC mode** | `pi --mode rpc`: JSON records, one per line, over stdin and stdout. pi defines the protocol; gentle-shell adds no command or event type of its own. It is not tRPC. | [04](04-rpc-contract.md); `pi@d86654a:packages/coding-agent/src/modes/rpc/rpc-types.ts:20-74` | The desktop's only formal interface to the runtime. It uses 3 of 33 commands ([04 §At a glance](04-rpc-contract.md#at-a-glance)). |
| **`setWidget`** | A fire-and-forget extension UI method carrying `widgetKey` and `widgetLines: string[]`. Under RPC, a widget given as a component factory instead of `string[]` is silently dropped.
